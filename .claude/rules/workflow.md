# Workflow — 研究判断与执行范围

## 开始与推进

读当前请求、项目入口及已有 PROJECT_BRIEF；有主稿时先确认指定版本。先解释经济问题，再选工具。用户已给充分要求就执行，不按文件数强制访谈。明确要求 plan-first 的任务，写入 `quality_reports/plans/YYYY-MM-DD_<task>.md`，状态 DRAFT；确认后标 APPROVED 并连续完成范围内工作。普通短任务不用独立计划。

每个工作块回答一个有价值的问题：当前判断是什么，依据和主要反证是什么，哪一步最能区分竞争解释。初期允许大胆发散，实施围绕一个暂定主线；备选方向保留触发条件，不自动展开。结果不支持原机制时更新解释，不更换验收目标以迎合预期。

核心问题、主要 estimand、影响解释的样本/主规格、昂贵新方向或对外行动需要具体依据和用户选择；已有授权有效，不重复问。写出推荐、替代方案、知识增量和代价。常规修复、局部编辑和必要检查直接做。

## 依赖按内容判断

文献与数据评估可以并行；结果依赖数据和已说明的规格。提纲、构想稿和理论稿不等最终回归，但不能填写虚构结果。同行审查以实际稿件、代码/日志为输入；没有执行证据就报告 NOT_RUN。提交包准备与真正向外提交是两件可分别授权的事。

每次只派有具体独立任务的 agent；主线程整合证据、处理分歧并向研究者解释。主线程也负责检查 worker/critic 的错误。小修改不启动完整流水线。详见 `agents.md`、`quality.md`。

## 状态与恢复

当前研究状态在 `research/PROJECT_BRIEF.md`；证据和决定按需维护于同目录。文件位置与身份见 `.claude/references/research-collaboration.md`。操作日志不代替研究判断；只读最近必要信息，不按任意回合数重开会话。

计划需要恢复指针时用 `.claude/state/active-task.json`，包含 `project_root`、`plan_path`（项目相对路径或 null）、`task`、`next_action`；实际会话 ID 可得时增加 `session_id`。不知道时不编造。hooks 只能保存已有状态，不能替用户批准计划或执行 `/checkpoint`。压缩前主动 checkpoint；恢复后核对用户最新任务、git diff、指针与当前证据。父目录、其他项目或其他会话的记录不作为本会话授权。

## 完成

运行与变更有关的检查，说明结果与未覆盖部分；必要检查通过后不反复扩大工作。只有有价值的修复才追加一轮，无进展时提供具体证据和选择。按既有授权保存、commit/push；不由“just do it”推断正式投稿、发信或合并他人 PR 的授权。
