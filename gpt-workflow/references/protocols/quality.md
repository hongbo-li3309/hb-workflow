# Quality — 检查证据，不给研究自动打分

## 状态

| 状态 | 含义 |
|---|---|
| PASS | 本次范围内的检查完成，有可定位证据 |
| FAIL | 检查完成，发现与要求矛盾的具体结果 |
| NOT_RUN | 未执行/无法执行/缺少执行证据，写出原因 |
| NOT_APPLICABLE | 对此产物不适用，写出理由 |
| STALE | 曾有检查，但相关输入/代码/规格/主稿已改变，需要重验 |

检查要注明目标版本、范围、方法与证据路径。状态不是模型对整篇论文的可信概率；单项 PASS 不能认证可发表、因果识别或全部复现。未核验的必要部分不得从汇总中消失。

## 审查发现

- **实质错误**：可定位、可复现或有明确原文依据的问题，说明对结论的影响。
- **证据缺口**：尚不能排除的威胁，区分已证实错误与审稿者的怀疑；给出什么证据会改变判断。
- **编辑建议**：改善表达、组织、格式或阅读体验，不伪装成方法硬要求。

每项主要发现附位置、理由、影响和最小可行修复。严重性来自后果，不来自激烈语气、作者声望或期刊名称。对反直觉、零或反向结果先核查，不以符号“正确”评分。

## 按用途判断是否完成

局部文字编辑核对原意与版本，不要求跑无关分析。探索可以保存未完成成果，并标清缺口。报告一个可靠结果需要实际证据、检查与限定；正式投稿前所有适用的关键问题需要解决或如实披露。Git 保存工作进度不等于宣称研究完成。

静态检查、程序运行、数值重现、识别/证明判断和文风审查分别记录。图表存在不证明本次运行成功，两份实现一致不排除共同错误。数字核对允许说明清楚的舍入，禁止单位变换错误和旧结果混入。

使用 `templates/quality-report.md`；轻量任务可直接在回复中报告，不必生成文件。工作流库维护使用 `scripts/validate_workflow.py` 和相应 tests；初始化后的研究项目只运行实际分析／稿件检查，必要时由 `scripts/run_check.py` 记录证据。这些检查不能认证创新性或“去 AI 味”。
